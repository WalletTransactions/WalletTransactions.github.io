# Из чего состоит

Продукт — набор клиентов и собственный серверный стек из независимых
сервисов. Каждый сервис отвечает за одну функцию.

```mermaid
flowchart TB
    subgraph Clients["Ваши устройства и ассистенты"]
        APP["📱 Android<br/>полная база на устройстве"]
        WEB["🌐 Веб-кабинет"]
        TG["💬 Telegram"]
        ASSIST["🤖 Claude, LM Studio<br/>и другие MCP-клиенты"]
    end

    subgraph Home["🏠 Ваш сервер"]
        GW{{"🚪 Шлюз<br/>проверяет пропуск"}}
        subgraph Write["Запись данных"]
            AUTH["🔑 Вход и аккаунты"]
            LEDGER["📒 Учёт и синхронизация"]
        end
        subgraph ReadOnly["Только чтение"]
            REPORT["📊 Отчёты"]
            MCP["🔌 MCP-сервер"]
            AI["✨ ИИ"]
        end
        BOT["💬 Бот"]
        DB[("🗄 База данных")]
    end

    LLM["🧠 Языковая модель<br/>на вашей видеокарте"]
    NET["🌍 Интернет: вход через Google,<br/>курсы валют, Telegram"]

    APP -- "синхронизация" --> GW
    WEB -- "кабинет" --> GW
    ASSIST -- "MCP + личный токен" --> GW
    TG <-- "сообщения" --> BOT

    GW --> AUTH & LEDGER & REPORT & AI & MCP
    BOT --> LEDGER & REPORT & AI
    MCP --> REPORT
    AI --> LLM

    LEDGER == "пишет" ==> DB
    REPORT -. "читает" .-> DB
    AUTH -.-> NET
    LEDGER -.-> NET
    BOT -.-> NET
```

Сплошные стрелки — запросы, жирная — запись, пунктир — чтение и редкие
обращения в интернет. Всё, что внутри рамки «Ваш сервер», работает у вас дома.

## Как ответ доходит из базы до ассистента { #mcp-answer }

Вы спрашиваете Claude или LM Studio о своих деньгах — модель не считает сама,
а вызывает инструмент кошелька и пересказывает готовые цифры:

```mermaid
sequenceDiagram
    autonumber
    actor U as Вы
    participant C as Claude / LM Studio
    participant G as Шлюз
    participant M as MCP-сервер
    participant R as Отчёты
    participant D as База
    U->>C: «Сколько ушло на кафе летом и зимой?»
    C->>G: вызов инструмента + личный токен
    G->>M: пропуск проверен
    M->>R: запрос отчёта (только чтение)
    R->>D: суммы считает база
    D-->>R: итоги по месяцам
    R-->>M: цифры, период и валюта
    M-->>C: результат инструмента
    C-->>U: ответ своими словами
```

Живые примеры таких ответов — на странице [«Как это выглядит»](showcase.md).

## Клиенты

| Компонент | Роль |
|---|---|
| **Android-приложение** | Основной клиент: полная база на устройстве, ввод, отчёты, курсы, ИИ, импорт выписок |
| **Веб-кабинет** | Аналитика, управление доступом, курсами, валютами, настройками и подключениями |
| **Telegram-бот** | Быстрый ввод трат, краткие отчёты и вопросы |

## Серверные сервисы

| Сервис | Функция |
|---|---|
| **Шлюз** | Единая точка входа: маршрутизирует запросы и проверяет пропуск пользователя |
| **Вход и аккаунты** | Вход через Google, сессии и устройства, роли, привязка Telegram, MCP-токены |
| **Учёт и синхронизация** | Хранит кошельки, категории и операции; принимает и раздаёт изменения устройствам; совместный доступ и приглашения; валюты, курсы и иконки |
| **Отчёты** | Все расчёты — остатки, обороты, структура, динамика, поиск. Только чтение |
| **ИИ** | Разбор трат и выписок, ответы на вопросы; единственный, кто обращается к языковой модели; ничего не записывает |
| **MCP-сервер** | Отдаёт ИИ-ассистентам инструменты кошелька, только чтение |
| **Бот** | Обрабатывает сообщения Telegram и действует от имени пользователя как ещё одно устройство |

## Принципы устройства

- **Запись и чтение разделены.** Пишет только сервис учёта, отчёты читают ту
  же базу ролью без права записи.
- **Пропуска выдаёт один сервис**, остальные проверяют их сами. Каждый
  сервис получает только те права, которые ему нужны.
- **Синхронизация пачками**: устройство отправляет свои изменения одной
  транзакцией и забирает чужие; повтор отправки ничего не дублирует.
- **Наблюдаемость**: метрики, журналы, версии и самоописание API у каждого
  сервиса.
